## 第 1 条（影响实现，建议改）：`priority` 默认 `MEDIUM` 让"没选"和"选了中"变得不可区分

- **问题**：契约 §1 把 `priority` 默认值定为 `MEDIUM`。统计时只能看到"中"，无法回答"有多少任务是用户真的选了中，多少是没填"。
- **影响**：US10 的 `byPriority` 会把所有旧任务和漏填任务都算进"中"，评审时若被问"中为什么这么多"，只能回答"因为默认值"。我在实现里暂时按契约处理（缺失记 MEDIUM），但这属于**统计失真**。
- **建议**：`priority` 默认改为 `null`（未设置），前端显示「未设置」，统计里单列一档「未设置」。若担心改动大，退而求其次：保留默认 `MEDIUM`，但在契约与表 4 验收标准里明确写"未选即视为中，界面上要显示为已选中"，避免"界面上是空的、数据里是中"的错觉。
- **需要拍板**：朱传玺（实现）/ 何健翔（统计口径）

## 第 2 条（影响实现，建议改）：契约没有"修改属性"的接口，US06 只能用不能改

- **问题**：契约 §3 写明"本轮只做创建时设置 + 列表显示，不做单独的编辑优先级/截止时间接口"。但 US06 的标题是"任务优先级与截止时间"，用户建完发现优先级选错，就改不了。
- **影响**：①评审演示到"改一下优先级"时会卡住；②US10 的数字只能反映创建那一刻的值；③若教师问"这算完成吗"，只能靠"范围声明"解释。
- **建议**：补一个 `PATCH /api/tasks/:id`，做**属性部分更新**（`priority`/`dueDate`/`iterationId`/`title`/`description`），**不改 `status`**（状态仍走 `PATCH /:id/status`，语义不重叠）。实现成本约 15 分钟，朱传玺在 `routes/tasks.js` 里加一个 handler 即可；测试补 3 条（合法更新、非法值 400、不存在 404）。
- **如果决定不做**：请在契约与表 3/表 6 明确写"US06 本轮为创建时设置，属性修改列入 Sprint 3 Backlog"，并把它登记为技术债（功能缺口），别留成"评审时才发现"。
- **需要拍板**：朱传玺（成本）/ 何健翔（范围）

## 第 3 条（影响实现，建议改）：逾期判定与日期时区没定，前端和统计会算出两个答案

- **问题**：契约 §3 只定了格式 `YYYY-MM-DD` 与"真实日期"，没定"今天"按哪个时区、逾期怎么比。
- **影响**：`new Date('2026-10-20')` 按 UTC 解析，在 +08:00 下会差 8 小时；若前端用 `Date` 比较、统计里用字符串比较，同一任务会一个显示"今天到期"、一个显示"已逾期"。
- **建议**：契约补一句：**"逾期以本地日期为界；`dueDate` 为纯日期字符串，直接按 `YYYY-MM-DD` 字典序比较，不构造 `Date` 对象。"** 这样前端、统计、测试三处口径一致，也省掉时区讨论。
- **需要拍板**：朱传玺（US06 展示）/ 何健翔（统计）

## 第 4 条（影响集成，建议补）：`iterationId` 与 `/api/iterations` 的约定缺失

- **问题**：契约 §4 只说 `iterationId` 引用 `iteration.id`、可空；§5.4 把 `/api/iterations` 推给彭佳成"不在本契约展开"。结果是：**引用不存在迭代时返回什么、`iterations` 对象有哪些字段，契约里没有**。
- **影响**：我在 `byIteration` 里只能自定义回退名「未知迭代 #id」；彭佳成若把 `iterations` 的字段起成 `iterationId` 而不是 `id`，统计立刻取不到名字。
- **建议**：契约补三行：
  1. `iterationId` 非空且迭代不存在 → `400 "非法迭代: <id>"`（与 `priority`/`dueDate` 的文案风格一致）；
  2. `Iteration` 最小字段 `{ id: number, name: string }`，其余字段（起止日期等）本轮不加；
  3. `GET /api/iterations` → `200` 返回数组，空则 `[]`。
- **需要拍板**：朱传玺（契约）/ 彭佳成（实现）

## 第 5 条（影响集成，**必须改**）：`db.js` 的 `readData()` 会把 `iterations` 丢掉

- **实测证据**（`docs/evidence/sprint2-us10-api-demo-20261017.txt`）：数据文件里明明有 `iterations: [{id:1,name:"Sprint 1"},{id:2,name:"Sprint 2"}]`，接口返回的却是 `"未知迭代 #1"`、`"未知迭代 #2"`。

原因在 `src/db.js` 第 47—50 行：

```js
return {
  members: Array.isArray(parsed.members) ? parsed.members : [],
  tasks: Array.isArray(parsed.tasks) ? parsed.tasks : [],
};
```

它按白名单挑字段返回，**契约里新增的 `iterations` 不在白名单，读出来就没了**。契约 §6 写的是"需兼容旧文件缺 `iterations` 的情况"，容易被理解成"读的时候不用管"，实际必须**加进返回值**：

```js
iterations: Array.isArray(parsed.iterations) ? parsed.iterations : [],
```

- **影响**：不改这一行，即使彭佳成的迭代功能做得完全正确，统计页永远显示"未知迭代"；评审演示到「按迭代统计」这一步会当场翻车。
- **验证命令**：`curl http://localhost:3000/api/stats`，看 `byIteration[].name` 是 "Sprint 2" 还是 "未知迭代 #2"。
- **需要拍板**：朱传玺（他改 `db.js`）

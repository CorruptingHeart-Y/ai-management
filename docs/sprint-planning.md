## 二 Sprint Goal 与范围依据

Sprint Goal：在本地演示环境中完成查看项目成员 → 创建并分配任务 → 更新任务状态，形成可运行、可测试、可演示的最小功能闭环。

实验一正式规划将首个 Sprint 定为这三个故事，后续再加入登录、权限、任务属性、迭代管理和统计。本轮复用预置四名成员，不实施成员新增、登录、复杂权限、评论、上传或统计。首个切片先验证成员与任务的关联和状态持久化，避免在基础流程尚未连通前同时展开权限与多项目功能。

本次以实验一正式项目规划、当前仓库故事编号和实际实现为基线。另有早期用户故事地图采用不同编号与更大首轮范围，不与正式规划混用。技术栈是在执行阶段明确的，不能把最终方案写成实验一已确定的技术决策。

## 四 工作拆分与执行中的完善

US01 的基础工作是建立 Member 的 id、name、role 契约，提供 GET /api/members，将成员姓名与分工显示在页面，并让 US04 负责人下拉框使用同一响应。后续 US01 增强提交 8109119 补充了重复 id 和非法字段校验、空列表、加载失败与重试、禁止无效分配、成员读取不改写数据等边界测试。这些是实施中的完善，不是未经记录的原计划承诺。

US04 建立 Task 的 id、title、description、assigneeId、status 字段，createdAt 为实现中的辅助字段。创建接口校验非空标题与有效成员，分配自增 id，写入统一 JSON 数据文件；原生页面提供表单、任务列表和负责人选择。正常创建、非法输入、再次读取及持久化由五项测试支撑。工程基础与成员预置数据先供并行开发复用，再由 US01 完善成员能力。

US05 统一 TODO、DOING、DONE 状态，提供合法性检查、状态更新领域逻辑、PATCH /api/tasks/:id/status 与页面切换，将状态写回同一数据文件。测试覆盖两个主要状态转换、非法状态和不存在任务。集成时移植状态逻辑而非保留分支中的独立存储，实现后续共享数据方案的一致性。

## 五 最终采用的技术方案

后端使用 Node.js 与 Express，前端为原生 HTML、CSS、JavaScript，持久化使用单个 JSON 文件；模块采用 CommonJS，测试使用 Node 内置 node:test 和 fetch。package.json 要求 Node.js 18 或以上，npm ci 安装锁定依赖，npm start 启动，npm test 执行三个故事的测试文件。

该方案适合本地课程原型：无前端构建环节、无需数据库服务，接口和文件数据都能直接核验。createApp 可注入 dataFile，自动测试使用隔离临时文件，避免写入演示数据。单文件同步读写不提供生产级并发、事务或访问控制，这一取舍只适用于当前小范围演示，不代表后续上线方案已确定。

Member 为 id、name、role；Task 为 id、title、description、assigneeId、status、createdAt。assigneeId 引用当前 Member.id。成员的 role 是人员分工说明，不是访问权限。三个故事共用 src/db.js 和同一数据文件，避免成员显示、负责人选项和任务归属各自维护一套数据。

## 六 依赖与集成风险

业务依赖为 US01 → US04 → US05。US04 需要真实成员才能分配，US05 依赖已创建任务及统一状态字段。并行开发可以先使用约定的预置数据，但集成必须统一模型、路由、页面和测试入口。

实际 US04/US05 合并提交 79948a5 记录了 package.json、package-lock.json、src/app.js、任务路由、页面与 AI 记录等共享文件冲突。两者虽都使用 Node.js，存储位置、测试工具和接口落点仍不同。集成保留 US04 工程与公共数据层，将 US05 状态逻辑、接口和页面能力移入，最终统一 node:test。后续 US01 经 integration/us01-merge 预检后合入 develop，没有文本冲突；无文本冲突仍需验证成员来源和完整业务链路。

AI 输出需要检查范围、字段和异常行为，不能因能启动或自动测试通过就视为完成人工审查。原始会话记录不完整、公共文件协调不够前置、集成时间未明确保留，均会增加追溯和交付风险。
